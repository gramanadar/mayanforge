Incremental Implementation Blueprint v1.2 · Approach B

Build the complete structural skeleton, prove a real end-to-end software-delivery workflow, then expand without losing planned capabilities. Companion to Master Capability Registry.

Design proposal, not implementation evidence. This plan is derived from the six uploaded files and adds proposed execution sequencing. Existing v2.3/v3.3 documents remain the detailed architecture references. Milestone numbering here is a consolidated plan, not a verbatim replacement of their separate roadmaps.

Non-negotiable rules

  1. Do not delete or silently downgrade a deferred capability; maintain a permanent source-linked registry.
  2. Keep logical modules separate from deployable services. Start with three main applications, plus Temporal, data infrastructure and isolated sandbox/test runners.
  3. Layer 2 owns authoritative business state, approvals and admission; Layer 3 owns execution state and evidence production; Layer 1 is not authoritative.
  4. Human approvals bind to exact immutable versions; changed digests invalidate downstream evidence and gates.
  5. Independent Verification cannot be self-certified by the code-writing agent; missing evidence is never PASS.
  6. All real code execution is isolated, policy-scoped, observable and bounded by budget.
  7. Do not implement all 15 role families as separate services. Register roles as Harness profiles.

Initial deployable topology

App 1 — Web: Next.js UI, six-stage navigation, progress and approvals.

App 2 — Business: Java 21/Spring Boot modular monolith: identity, organizations, projects, SDLC, approvals, artifacts, budgets, event inbox/outbox and REST/SSE.

App 3 — Execution: Java 21/Temporal workers: orchestration, Agent Harness, roles, skills, context, tools, evaluations, Watchdog and evidence coordination.

Separate runtime boundaries: Temporal Server, PostgreSQL, object storage, sandbox executors and independent verification workers. These are not all additional business microservices.

Important: Independent verification requires distinct permissions and execution environment; a separate source repository or full microservice is not required initially.

Eleven gated milestones (M0–M10)

M0 · Source reconciliation & contracts

Deliver: Full atomic registry; ownership map; canonical command/event schemas; versioning; threat model and ADRs

Exit gate: Contract fixtures reject malformed, cross-tenant and stale version inputs; every initial UI action has an authoritative backend path.

M1 · Running foundation

Deliver: Monorepo; Next.js shell; Spring Boot business service; Java/Temporal worker; PostgreSQL; local Docker; CI; tracing

Exit gate: Real request creates durable workflow and projects status back to UI; worker restart does not lose execution.

M2 · Business authority

Deliver: OIDC/BFF; organization/project authorization; revisions; immutable approvals; artifact metadata; outbox/inbox; budget admission

Exit gate: Cross-project access denied; stale revision approvals rejected; duplicate command has one logical effect.

M3 · Real trusted Harness

Deliver: Role profile; versioned skill lock; tool policy; isolated sandbox; Git branch; receipts; bounded context and spend

Exit gate: Backend agent commits working code to test repository with compile/test receipts; denied tool access remains denied.

M4 · First six-stage vertical slice

Deliver: Intake manifest; requirements baseline; proposal selection + design approval; Build plan and task review; independent verification; release package

Exit gate: One small task traverses all six stages; no mock pass; unreviewed code cannot merge; sign-off matches candidate digest.

M5 · Defect and recovery path

Deliver: Independent failure verdicts; defect records; human-triggered repair; retries and dedup; basic watchdog; event replay

Exit gate: Inject test failure, worker death, stale approval, missing evidence and duplicate event; system remains safe and recoverable.

M6 · MF-001 pilot

Deliver: RAG 10 docs, classification up to 5 categories, mock CRM read/draft/approved write, n8n, React UI, evaluations, audit and handoff

Exit gate: Demonstrate complete MF-001 acceptance criteria with measured cost, recovery, security and evidence.

Contracts to freeze before agent implementation

Commands: ExecutionCommand (workflowKind, subject revision/digest, project/tenant identity, idempotency, budget and policy references), approval decisions, task review decisions, repair requests and human signals.

Events: StageOutputProduced, workflow/task status, candidate manifest, verification results, defects, watchdog state, artifact receipts and usage accounting.

Versioning: immutable artifacts, subject-bound approvals, stage reopen/invalidation, task predecessor rules and candidate-bound verification/sign-off.

API: freeze actual OpenAPI and JSON Schemas from Layer 2 section 12 and Layer 3 cross-layer contract sections; use generated fixtures and compatibility tests.

Open design decisions: OIDC provider, sandbox threat model, artifact storage, broker vs PostgreSQL outbox, Temporal deployment, release targets and precise service-to-service auth must be decided or timeboxed before production use.

Expansion without feature loss

Every new role, skill, stage activity or integration must begin with a registry entry, source trace, impact analysis, contract diff and acceptance tests. Build extensions as stable module interfaces and versioned contracts; introduce separate deployments only when measured security, scaling, failure isolation or lifecycle requirements justify them.

Change checklist: source intent preserved → owning layer identified → API/event changes reviewed → migrations safe → permissions checked → state/invalidation effects checked → evidence/test catalog updated → UI coverage checked → release notes and registry updated.

Future integrations: AKE and Architecture Decision Intelligence are recorded as planned expansion, not silently folded into initial delivery. Their approval-governed knowledge publication must remain separate from automated agent execution.

Release and milestone gates

  • No fabricated agent runs, test results, completion states or verification PASS.
  • Every human gate must be durable, version-bound, authorized and auditable.
  • Unreviewed tasks do not merge; failed integration does not auto-repair without the required human decision.
  • Retryable commands are idempotent; external side effects are reconciled after crashes.
  • Project and tenant boundaries hold under API, event and artifact access tests.
  • Every milestone has a demonstrable end-to-end scenario and negative tests.
  • At each release publish coverage counts: Cataloged / Contracted / Implemented / Verified / Deferred / Blocked / Superseded.

A single MF ID can require tasks in multiple milestones; its target milestone represents the principal delivery point, not permission to defer earlier safety prerequisites.

M7–M10: Explicit expansion milestones

M7 · Collaboration, change management and organization expansion

Deliver: Extend collaboration and change management, preserving tenant permissions, versioning, and approval invariants.

Exit gate: Demonstrate authorized multi-user collaboration and safe change propagation without regressing M0–M6.

M8 · Agent role families, skills and context expansion

Deliver: Add further role profiles, skills and context capabilities through the shared Harness; no per-role microservices.

Exit gate: New role and skill packages execute under existing policy, version locks, budgets and test evidence.

M9 · Advanced observability, governance and Watchdog

Deliver: Extend operational telemetry, audit, policy controls and progress-aware monitoring; retain minimum safeguards in earlier milestones.

Exit gate: Fault-injection, escalation and policy tests pass without unsafe automatic recovery.

M10 · Ecosystem, event automation and continuous improvement

Deliver: Extend integration adapters, automation, and governance-controlled knowledge/decision reuse where included in approved atomic scope.

Exit gate: Integrations meet idempotency, security, rollback, human approval and end-to-end evidence requirements.

Cross-document synchronization and completion policy

  1. Use the registry JSON as the only editable source for MF ID, target milestone and status; generate HTML views and milestone summaries from it.
  2. Before a milestone begins, review every assigned MF ID, split broad section headings into atomic acceptance-testable requirements, and record parent/child traceability without deleting existing IDs.
  3. For each atomic requirement, record owner, dependency, API/event or UI touchpoints, coding-agent task ID, acceptance tests and evidence links.
  4. Mark a milestone complete only when required capabilities pass their gates; record exceptions as explicitly approved, visible deferrals with impact and a new target.
  5. Run automated coverage checks: all original MF IDs retained, each assigned to one primary milestone, no unknown milestone, no unapproved deletion, and every ready task linked to an atomic capability.
  6. Keep foundational security, independent verification, approvals, budgets, audit and sandbox protections in their earlier required milestones even when a related advanced section is mapped to M7–M10.

Revision note: v1.2 extends v1.0; M0–M6 deliverables, T-001–T-010 and architecture principles remain in force. M7–M10 sequencing is provisional until M0 dependency reconciliation.
