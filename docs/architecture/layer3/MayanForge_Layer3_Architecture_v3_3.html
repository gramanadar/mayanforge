Layer 3 — Orchestration, Workers, Agent Harness & Stage Evaluation

Consolidated Layer 3 technical design. Preserves v3.0 execution architecture and integrates stage-specific Harness evaluation contracts across all six SDLC stages, Progress-Aware Watchdog refinements, and the v3.2/v3.3 reconciliation with UI v6–v7 and Layer 2 v2.3.

Version 3.316 November 2026Design proposal · not deployedJava-first
DESIGN / 01

Executive summary and reading guide

Decision: Retain the original v2.4 headless execution engine invariants, organize the implementation as a Web → Service → Orchestration/Workers system, and elevate the Agent Harness into the mandatory execution runtime. This document is the proposed Layer 3 v3.3 baseline, not a description of a running production system.

What stays

v2.4 durable workflow authority, least privilege, approved skill locks, evidence-bound evaluation, event router, interactive signals, watchdog and human gates.

What changes

Explicit Layer 2/3 ownership; Java 21 and Temporal Java as the leading implementation candidates; agent-harness lifecycle and runtime contracts.

What UI v6 contributes

Six visible SDLC stages; Build board (Plan → Approve → Run → Integrate) with per-task review; Verification steps (Plan → Execute → Evaluate → Sign-off); combined Architecture + System Design approval. UI is a behavioral reference, not execution proof.

How to read

Start with Architecture & Ownership, then Harness and Worked Scenario. Use the contracts, schema and failure tests for implementation.

Terminology: “Normative” means a proposed MayanForge design rule; “Candidate” means a technology not yet proven by a spike; “Prototype” means UI-only reference behavior; “Future” means explicitly out of MVP.

v3.1 addition: six stage-specific evaluation profiles reuse the trusted Harness Runtime; progress contracts and watchdog state are distinct from output evaluation and release-quality gate authority.

v3.2 reconciliation (11 November 2026): aligns Layer 3 with UI v6 and Layer 2 v2.2. Decisions: (1) Verification sign-off is a real human gate, separate from Release approval; (2) every Build task output requires human review before its pull request is merged; (3) repair is human-triggered after a failed integration or verification; (4) a single-approver policy is allowed in the single-tenant pilot. v3.2 also normalizes verdict vocabulary, the execution admission contract, agent role naming and table ownership. See ADR-017 to ADR-022.
v3.3 (16 November 2026): every UI action now maps to a Layer 2 endpoint and a Layer 3 workflow kind. Adds the generation workflows per stage — INTAKE_ANALYZE, REQUIREMENTS_DRAFT, ARCHITECTURE_PROPOSALS, SYSTEM_DESIGN_GENERATE (from the selected proposal), BUILD_PLAN, VERIFICATION_PLAN, CHANGE_IMPACT_ANALYZE, RELEASE_NOTES — and the StageOutputProduced event that hands drafts to Layer 2. Adds INTAKE_SCOPE and CHANGE_PLAN approvals, automatic dispatch after a single Build start, task retry and recovery-decision signals. See ADR-023 to ADR-025.

DESIGN / 07

Durable Orchestrator and DAG engine

Execution admitted
→
Plan proposed
→
Plan approved / frozen
→
Ready tasks scheduled
→
Harness attempts
→
Human review + merge
→
Integrate → frozen candidate
→
Independent gates
→
Completion or human-requested repair
  • Use deterministic workflow logic for state transitions, timers and scheduling; move LLM calls, Git, network, policy lookups and DB mutations to activities.
  • Each DAG node declares dependencies, role, immutable task contract, required gates and a maximum concurrency/budget envelope.
  • Ready means every predecessor task is SUCCEEDED, i.e. its stage evaluation PASSed and a human approved the output and its pull request was merged into the integration branch. An agent reporting completion is never enough.
  • Use explicit activity IDs, heartbeat timeouts, retries with bounded backoff, idempotency receipts and reconciliation for ambiguous external effects.
  • Use workflow versioning and replay compatibility tests before deploying workflow code changes.
  • A repair creates a new task attempt and potentially a new candidate digest; prior gate evidence is not transferable automatically.
  • Repair is human-triggered (ADR-019): after an integration failure or a failed verification the workflow enters REPAIR_REQUIRED and waits for a RepairRequest signal from Layer 2 naming the tasks to return. It never starts repair on its own.
  • Dispatch is automatic (ADR-024): a person starts the build once after plan approval (BUILD_EXECUTE); from then on every dependency-ready task is scheduled without further clicks. A person may retry a failed task (bounded by its retry policy) or cancel the run.
  • Generation workflows (ADR-023) are short single-task executions: one role profile, read-only access to the bound inputs, write access only to the output artifact, stage evaluation, then StageOutputProduced. They never approve or select anything.
Workflow states: RECEIVED → ADMITTED → PLANNING → WAITING_PLAN_APPROVAL → READY → RUNNING
  → INTEGRATING → CANDIDATE_FROZEN → WAITING_TEST_PLAN_APPROVAL → VERIFYING → WAITING_SIGNOFF → COMPLETED
Alternate: BLOCKED_APPROVAL | RETRY_WAIT | REPAIR_REQUIRED (waits for human RepairRequest) | FAILED | CANCELLED
Task states: PENDING → READY → LEASED → RUNNING → OUTPUT_VALIDATION → AWAITING_REVIEW → MERGING → SUCCEEDED
Alternate: RETRY_WAIT | CHANGES_REQUESTED (→ READY, new attempt) | BLOCKED | FAILED | CANCELLED

WAITING_TEST_PLAN_APPROVAL is satisfied immediately if the verification plan and thresholds were approved earlier (they may be approved while Build runs). Human waits (plan, every task review, test plan, sign-off) are healthy waits for the Watchdog, never stalls.

v3.1 evaluation hook: after artifact validation, invoke the applicable versioned stage evaluation profile. A FAIL produces a bounded repair attempt, INCONCLUSIVE blocks advancement pending evidence or human decision, and PASS advances only when required approvals and predecessor gates are satisfied. The stage evaluator never grants tool permissions or changes frozen requirements.

v3.2: in Build, a stage-evaluation PASS moves the task to AWAITING_REVIEW; it does not merge. The merge is a separate Tool Gateway action that requires a Layer 2 TASK_OUTPUT approval bound to the pull request head commit SHA and re-checks that binding at the point of effect. A new commit after approval invalidates the approval.

DESIGN / 10

Stage-Specific Harness Evaluation: six SDLC profiles

Normative proposal for v3.1: one shared Harness Runtime executes stage-specific evaluation profiles. Stage evaluators assess outputs and evidence, while the Watchdog monitors progress; only the Independent Evaluation Engine issues release-quality verdicts. These contracts and thresholds are proposals, not tested implementation.

The Watchdog observes the execution in parallel, issuing evidence-backed recommendations. It cannot approve artifacts, mutate code, bypass policy, or override stage/quality gates. Independent Verification executes separately on the pinned candidate.

Gate semantics: PASS = all mandatory checks have sufficient evidence; FAIL = a mandatory check fails; INCONCLUSIVE = evidence missing or test unable to run; BLOCKED = known unmet prerequisite or required approval. A stage may advance only if its mandatory gates PASS and required approvals are recorded.

Normative vocabulary (v3.2): these four are the only verdicts. Missing or unrunnable evidence is INCONCLUSIVE, never “Blocked”; BLOCKED is reserved for a known unmet prerequisite or approval. “Review required” is not a verdict: it is BLOCKED with reason HUMAN_DECISION_REQUIRED. NOT_RUN, RUNNING and STALE are Layer 2 display states for projections, not verdicts.

Monitoring states: HEALTHY → SUSPECT → STALLED → RECOVERING → HEALTHY or ESCALATED. This is a separate projection from authoritative workflow states. Require sustained evidence (hysteresis), cooldowns and idempotent intervention receipts; observe recovery outcome before another intervention.

Recovery permissions: Watchdog recommends; policy authorizes; Orchestrator schedules; Harness executes bounded retries or diagnostic tasks; Stage Evaluator reassesses output. Budget increases, permission expansions and human-gate overrides are prohibited without explicit authorization.

13 · Required acceptance and failure-injection tests

  1. Missing intake source or CRM credentials yields BLOCKED/INCONCLUSIVE, never invented PASS.
  2. Requirements with conflicting acceptance criteria cannot advance without resolution or approved explicit exclusion.
  3. Architecture missing a mandatory requirement mapping fails its stage gate.
  4. Build agent reports “done” but compilation fails: stage gate FAIL; repair is bounded.
  5. Repeated identical failures with healthy heartbeats trigger SUSPECT/STALLED after configured window, not immediate infinite retries.
  6. Long-running test with valid progress evidence remains HEALTHY.
  7. Verification has missing test evidence: INCONCLUSIVE; candidate mutation invalidates prior gates.
  8. Watchdog intervention is duplicated or arrives out of order: one authorized logical action only.
  9. Release approval for old candidate digest cannot authorize a new candidate.
  10. Human approval wait never triggers stall-based unauthorized progression.
  11. Injected instructions in repository or test logs cannot expand tool scopes.
  12. Worker restart preserves checkpoints, leases and evaluation provenance.
  13. A task output that passed stage evaluation but has no human review cannot be merged and cannot unblock dependents.
  14. A review approval for an older PR head SHA cannot merge a newer commit.
  15. A failed verification never starts repair until a human RepairRequest is recorded.
  16. A sign-off for candidate rcN cannot be used to release rcN+1.

Example policy (proposal, not validated): after three materially identical failed attempts without new evidence, request an alternate plan; after a bounded second window, stop and escalate. The watchdog may recommend recovery but cannot expand tool scopes, waive quality gates or override human approval.

Monitoring states, decision ordering and anti-loop safeguards (v3.1)

Watchdog state is separate from workflow state: HEALTHY → SUSPECT → STALLED → RECOVERING, with ESCALATED for unresolved or unsafe conditions. WAITING_FOR_APPROVAL or an authorized dependency wait can remain healthy. The Watchdog only recommends; policy authorizes; the durable Orchestrator applies recovery; independent evaluation decides quality.

  • Reject stale/duplicate events; validate run, attempt, source and lease before evaluating progress.
  • Check hard budget/cancellation constraints and intentional waits before classifying stagnation.
  • Use stage-specific progress contracts, rolling windows, error fingerprints, hysteresis and cooldowns; do not treat file churn or heartbeats alone as progress.
  • Persist evidence-backed recommendations and idempotency keys; fence stale workers; observe recovery outcome before another intervention.
  • Track stall detection latency, false-positive interventions, recovery success, repeat-recovery loops and resource savings against a baseline.

v3.2 visibility: every transition to STALLED or ESCALATED emits a WatchdogStateChanged event with execution, task, attempt, reason, recommendation and evidence references. Layer 2 projects it to Monitoring and notifies the project; a person may cancel, or authorize the recommended recovery through an authenticated signal. Without a person, an ESCALATED execution stays stopped.

Environment: verification runs in an isolated namespace per candidate (fresh database, synthetic fixtures, mock external systems, pinned AI configuration) with no access to Build agents or their claims. Defect ownership: owning tasks are proposed by tracing failed test → requirement → task links; a person may reassign them before requesting repair. Candidate integrity: if Build modifies the integrated candidate after tests, previously collected gate evidence must not be reused to approve the changed bytes.

Boundary with stage evaluation: Build checks engineering readiness and may run integration/E2E tests; Verification independently plans risk- and requirements-based tests, runs them on the exact pinned candidate, and issues evidence-backed gates. Passing Build tests never substitutes for independent Verification. Verification does not silently edit the candidate; repairs return to Build and create a new digest.
