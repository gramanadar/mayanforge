Layer 2 — Service Architecture v2.3

Comprehensive, understandable Java-first service design connecting the Web experience to durable Layer 3 orchestration, agent Harness and independent Verification.

31 sectionsProposed · Not implemented16 November 2026

01 · Executive summary and reading guide

Layer 2 is the trusted business application boundary between the Web UI and the headless Layer 3 execution engine. It governs projects, SDLC records, versions, human decisions, policy-aware execution admission, and user-facing projections. Layer 3 owns workflow execution, Harness, agents, workers, and independent evaluation.

Design status: Proposed architecture, not a running implementation. This document reconciles the earlier Layer 2 draft, Layer 3 v3.3, the older execution-engine v2.4 principles, and the UI v6 prototype workflow. Illustrative APIs and SQL are not deployed endpoints.
v2.2 changes (11 November 2026): aligned with UI v6 and Layer 3 v3.2. New human gates and records: Build plan approval, mandatory review of every task output before merge, verification plan and threshold approval, verification sign-off (separate from Release), and human-triggered repair. Adds defects, integration runs, the extended candidate manifest, stage assistant requests, architecture proposals and opportunities. Normalizes the execution admission API, status and verdict vocabulary, and JSON casing. A single-approver policy is allowed in the single-tenant pilot.
v2.3 changes (16 November 2026): every UI action now traces to a named Layer 2 endpoint and a Layer 3 workflow kind. Adds draft generation commands for every stage (intake analysis, requirements, architecture proposals, system design from the selected proposal, build plan, verification plan, release notes) and the StageOutputProduced event that turns Layer 3 output into Layer 2 draft records. Adds the Architecture & System Design model (proposal → system design → ADRs, with human ADR edits), change requests with impact analysis and a CHANGE_PLAN approval, the INTAKE_SCOPE approval, an explicit reopen and invalidation cascade, Build start and task retry, verification run start, and decisions on escalated executions.

02 · Scope, invariants and non-goals

Layer 2 owns

  • Tenant/project membership, project metadata and SDLC business records
  • Requirement, architecture, plan and candidate versions; approval decisions
  • Task review decisions, verification plan approvals, verification sign-offs, defect triage and repair requests
  • Stage assistant questions and revision requests; opportunities (pre-project ideas)
  • Execution intent and admission decisions; idempotent commands to Layer 3
  • Read models for runs, tasks, verification, evidence and costs
  • Human-friendly status, notifications, audit and artifact access policies

Layer 2 does not own

  • Temporal workflow history, DAG scheduler, agent reasoning loop, skill execution
  • Untrusted code sandbox, tool execution, LLM calls or independent gate verdict computation
  • Final authority to bypass Layer 3 Tool Gateway policy
  • Production deployment without explicit artifact-bound authorization
Non-negotiable: an HTTP 202 response means accepted for processing, not completed. An agent-produced “pass” is not independent verification evidence. A human approval never silently changes the artifact/version it approved.

Do not create two competing state machines. A Layer 2 stage can be “Verification” while the Layer 3 workflow is “WAITING_TEST_PLAN_APPROVAL” or “VERIFYING”; those describe different concepts. Layer 2 must never overwrite a workflow status from an assumed UI action.

06 · Project and SDLC domain model

A project follows six user-facing stages: Intake → Requirements → Architecture & System Design → Build → Verification → Release. Stage advancement is a guarded business transition, not an automatic side effect of a page click.

StageLayer 2 recordsGate to advance
IntakeProject charter, source inputs, scope, risk, intake manifestINTAKE_SCOPE approved (scope, inputs, exclusions, open questions)
RequirementsFR/NFR versions, criteria, traceabilityApproved requirements revision
Architecture & System DesignProposals, selected proposal, system design, ADRs, review notes, requirement-to-design coverageOne combined Architecture + System Design baseline approval; mandatory mappings complete; no open review notes
BuildApproved implementation plan, work packages, task views, task review decisions, integration runs, candidate manifestPlan approved; every task output reviewed and merged; integration pipeline passed; candidate frozen
VerificationVerification plan and thresholds, test catalog, evidence projections, independent verdict, defects, sign-offPlan and thresholds approved; required gates PASS (or authorized exception); human sign-off of the exact candidate
ReleaseRelease candidate, approvals, target, receiptVerification sign-off for the same candidate digest + human approval of exact candidate and environment

Guarded transition example

advance(projectId, targetStage, expectedVersion):
  verify actor permission and project tenant
  lock project aggregate / optimistic version
  verify current stage permits transition
  load required approved subject digests
  evaluate transition policy and evidence references
  write transition + audit + outbox in one transaction
  return new project version; never synthesize gate PASS

Draft generation: Layer 2 asks, Layer 3 writes (v2.3)

Layer 2 never calls an LLM. Each stage has a named generate command that checks permission, approved inputs and budget, then starts a Layer 3 execution through Execution Admission (§13) with the right workflowKind and subject binding. The agent’s output comes back as a StageOutputProduced event; Layer 2 stores it as a DRAFT business record that people review, edit, select and approve. Generated drafts never approve themselves.

Reopen and invalidation cascade (v2.3)

Reopening an approved baseline never edits it: it creates a new DRAFT revision and marks everything that depended on the old digest as STALE, in the same transaction as the reopen and its outbox event.

When a person reopens…Becomes STALE / must be approved again
Intake scopeRequirements baseline and everything after it
Requirements baseline (“Request changes”)Architecture baseline, build plan, verification plan, candidate gates, sign-off, release
Architecture baseline (“Reopen technical design”)Build plan, merged-task reviews for affected work packages, verification plan, candidate gates, sign-off, release
Build plan (“Revise plan”)Not allowed while tasks are running; afterwards: integration, candidate, verification gates, sign-off, release
Approved change planCandidate, verification gates, sign-off and release; affected tasks re-enter Run

07 · Requirements and traceability services

Requirements are first-class, immutable revisions once approved. Store FR and NFR identifiers, priority, owner, acceptance criteria, measurable thresholds, dependencies, and source provenance. A new revision supersedes rather than mutates an approved revision.

EntityKey fields
requirement_revisionrequirement_id, revision, kind FR/NFR, text, status, source_ref, digest
acceptance_criterioncriterion_id, requirement_revision_id, measurable_rule, severity
trace_linkfrom_type/id/revision → to_type/id/revision; link_kind; reviewer
coverage_snapshotrequirements_digest, architecture_digest, coverage_percent, missing_mandatory[]
Coverage is not just a percentage: approving Architecture requires zero unaddressed mandatory requirements, or explicit documented exceptions under a defined policy.

08 · Architecture & System Design service

Architecture proposals, the selected system design, diagrams, ADRs, design decisions, review notes and requirement mappings are revisioned. The Review & Approval screen displays readiness checks and the coverage summary and allows detailed mapping inspection, matching UI v6.

  • Proposals: the Architecture Agent may produce several proposals; a person selects one. Selection is recorded but is not approval.
  • Review notes: design and proposal feedback are tracked items that must be resolved (or explicitly deferred) before approval.
  • Combined baseline: one approval covers the selected proposal, its system design and ADRs (subject kind ARCHITECTURE_BASELINE). Approving it unlocks Build planning; reopening it reopens the Build plan for approval.

Generate → select → design → decide → approve (v2.3)

  1. Generate proposals from the approved requirements baseline (ARCHITECTURE_PROPOSALS). A person may ask for a revised proposal with feedback; this creates a new proposal revision and supersedes the old one.
  2. Select one proposal (recorded, not an approval). Selecting another later supersedes any design generated for the previous one.
  3. Generate the system design for the selected proposal (SYSTEM_DESIGN_GENERATE): components, contracts, data flows, requirement-to-design mapping and proposed ADRs. Regenerating creates a new design revision.
  4. Decide ADRs: people edit ADR drafts (context, options, decision, consequences, risks, scope, linked components) and set their status. ADRs are versioned with If-Match.
  5. Review: review notes are added and resolved; readiness checks run (requirements approved, proposal selected, design generated, ADR decisions recorded, no open notes, all requirements mapped).
  6. Approve ARCHITECTURE_BASELINE, bound to the proposal, design revision, ADR set and coverage digests.
ArchitectureProposal { proposalId, projectId, revision, title, summary, tradeoffs, artifactId, digest,
  status: DRAFT | SELECTED | SUPERSEDED | REJECTED, basedOnRequirementsDigest, sourceExecutionId }
SystemDesignRevision { designRevisionId, proposalId, revision, artifactId, digest,
  status: DRAFT | IN_REVIEW | APPROVED | SUPERSEDED | STALE, coverageSnapshotId, sourceExecutionId }
Adr { adrId, designRevisionId, title, context, options[], decision, consequences, risks,
  scope: SYSTEM | COMPONENT | CROSS, componentIds[], status: PROPOSED | ACCEPTED | REJECTED | SUPERSEDED,
  editedBy, version }
  • Freeze the design digest, requirements digest, reviewer identity and approval policy when creating an approval request.
  • Reject approval if the design changed, a mandatory requirement lacks coverage, or the request expired.
  • Record reviewer comments, rejected alternatives and unresolved risks.
  • On approval, emit a durable event that Layer 3 may use to resume an authorized waiting workflow.

Starting the run and retries (v2.3)

After BUILD_PLAN approval a person starts the build once (POST …/build/runs → BUILD_EXECUTE). Layer 3 then schedules every dependency-ready task automatically; there is no per-wave dispatch. A failed task can be retried in a new sandbox with POST …/build/tasks/{taskId}/retries (bounded by the task's retry policy). A person can still cancel the run.

Change requests (v2.3)

Feedback raised after baselines exist (“Request a change”) becomes a ChangeRequest. Layer 3 analyses its impact (CHANGE_IMPACT_ANALYZE): affected requirements, design, ADRs, tasks and gates. A person approves the resulting change plan (subject kind CHANGE_PLAN); this creates a new plan revision with the new or changed tasks and applies the invalidation cascade (§06). Rejected or withdrawn requests change nothing.

ChangeRequest { changeId, projectId, text, raisedBy, status: PROPOSED | ANALYZING | IMPACT_READY |
  APPROVED | REJECTED | WITHDRAWN, impactAnalysisRef?, affected:{requirementIds[], adrIds[], taskIds[], gates[]},
  resultingPlanRevisionId?, version }

10 · Verification service: steps, human gates and defects

The six activities are internal to the single Verification stage, not six new SDLC stages. The UI presents them as four steps — Plan → Execute → Evaluate → Sign-off — with two human gates. Layer 2 exposes their progress and evidence without fabricating execution results.

Status vocabulary (shared with Layer 3 v3.2): verdicts are PASS, FAIL, INCONCLUSIVE (evidence missing or unrunnable) and BLOCKED (known unmet prerequisite or approval; “review required” is BLOCKED with reason HUMAN_DECISION_REQUIRED). Repair is human-triggered: “Send defects to Build” (or “Send tasks back to Run” after a failed integration) creates a RepairRequest; Layer 2 commits it with an outbox signal; Layer 3 returns the named tasks to READY. The new candidate is verified in full. A test-plan approval carries over only if its digest is unchanged.

Generation and runs (v2.3): the plan is drafted with POST …/verification/plan:generate (VERIFICATION_PLAN); people may adjust thresholds while the plan is a draft (PATCH …/verification/thresholds, If-Match); the plan and thresholds are then approved together. A run on the frozen candidate is started with POST …/verification/runs (VERIFICATION_RUN), allowed only with an approved plan.

11 · Agent, role and skill catalog APIs

Layer 2 is a catalog-facing service, not the authority that executes or loads skills. It may display the 15 logical role profiles, shared skill domains, individual approved skills, compatibility, provenance, versions and approval status.

  • Read APIs expose only authorized catalog metadata and immutable versions.
  • Skill publication is a human-governed process; the registry must enforce approved, digest-pinned versions.
  • A role may use many skills; a skill may be reused by many roles; domains are discovery metadata, not permission grants.
  • Execution requests identify a role profile and requested capabilities; Layer 3 independently resolves the allowed skill lock.
  • Named agents shown in the UI (Implementation Planning, Verification Planning, Integration Engineer, Release Assistant, stage assistants) are role profiles inside the 15 families, mapped in Layer 3 v3.2 §09. The Independent Evaluation Engine is a verification component, not an agent role, and must not appear as an assignable role.

12 · Public REST API design — complete service inventory

Scope: proposed API contract catalog, not implemented endpoints. Paths are illustrative and must be frozen in OpenAPI. Identity-provider-owned login, MFA, password reset, and token issuance are not custom MayanForge password APIs. MayanForge BFF endpoints manage application sessions. All tenant/project resource paths require authorization on every request.

Conventions: JSON over TLS; /api/v1; 202 Accepted for async operations; 201 for resource creation; cursor pagination; RFC 9457 problem details; ETag/If-Match for mutable versioned resources; Idempotency-Key for retriable commands; request_id and correlation_id; no secrets in logs. CSRF protection for cookie-authenticated mutations.

13 · Execution admission and Layer 3 command protocol

Execution admission validates project state, actor permission, approved inputs, policy, budget and idempotency. It writes a command to an outbox transactionally; a dispatcher delivers it to Layer 3. No remote workflow call should occur inside the project DB transaction.

POST /api/v1/projects/{projectId}/executions
Idempotency-Key: 6d3f...
{
  "workflowKind":"ARCHITECTURE_PROPOSALS",
  "stage":"ARCHITECTURE",
  "subjectRefs":[{"kind":"REQUIREMENTS_BASELINE","revisionId":"reqrev_17","digest":"sha256:..."}],
  "requestedRoleProfileId":"software-architect",
  "expectedProjectVersion":12,
  "budgetPolicyId":"budget_standard"
}

HTTP/1.1 202 Accepted
{
  "executionId":"exec_01",
  "admissionStatus":"ACCEPTED",
  "statusUrl":"/api/v1/executions/exec_01",
  "eventsUrl":"/api/v1/executions/exec_01/events"
}

Admission states (Layer 2 execution_requests.admission_state): ACCEPTED (intent, budget reservation and outbox committed) → DISPATCHED (delivered to Layer 3) → ADMITTED or REJECTED (Layer 3 decision, received as an event). Workflow progress after ADMITTED uses Layer 3 workflow states. workflowKind values are defined in Layer 3 v3.3 §18. The browser normally uses the named stage generate commands (§06), which build this command with the right workflowKind and subject binding; the low-level endpoint stays available for automation.

Wire format: all JSON on the wire, public and internal, uses camelCase field names; Layer 3 documents its contracts in snake_case with a 1:1 mapping. Enum values are upper-case and shared by both layers.

Canonical command envelope

ExecutionCommand {
  schemaVersion, commandId, commandType, workflowKind, tenantId, projectId,
  executionId, actorId, stageId, authorizedScope, subjectRefs[{kind, revisionId, digest}],
  inputArtifactRefs[], requestedRoleProfileId, budgetReservationId,
  policyVersion, idempotencyKey, issuedAt, expiresAt,
  correlationId, causationId
}
# delivered by the outbox dispatcher to Layer 3: POST /internal/v1/execution-commands (mTLS)
# approvals, task reviews, repair requests, cancellations: POST /internal/v1/signals
Layer 3 must verify the command origin, tenant binding, expiry, replay protection and effective execution authorization; Layer 2 approval does not confer unrestricted tool rights.

14 · Approval protocol and human gates

Approval is a business decision in Layer 2; the waiting workflow lives in Layer 3. A decision must be tied to an immutable subject and cannot be reused to approve changed artifacts.

REQUESTED -> APPROVED | REJECTED | EXPIRED | REVOKED
  subject: {kind, projectId, artifactDigest, revisionId,
            targetEnvironment?, operation?, policyVersion}
  decision: {approverId, decision, decidedAt, reason,
             subjectDigest, decisionId, authorizationSnapshot}
Subject kindBound toUnblocks
INTAKE_SCOPEIntake manifest digest (scope, inputs, exclusions)Requirements drafting
REQUIREMENTS_BASELINERequirements revision digestArchitecture
ARCHITECTURE_BASELINESelected proposal, system design, ADR set and coverage digestsBuild planning
BUILD_PLANPlan revision digestTask runs
TASK_OUTPUTTask ID, attempt ID, PR head SHA, validation evidence digestMerge of that task and its dependents (mandatory for every task)
VERIFICATION_PLANCoverage plan, test catalog and threshold digestsVerification execution
VERIFICATION_SIGNOFFCandidate digest, gate evidence digest, accepted-risk listRelease
RELEASECandidate digest, target environment, sign-off referenceRelease record (production deploy disabled in MVP)
CHANGE_PLANChange request + impact analysis digestNew plan revision; invalidation cascade
  • Approval creation records immutable subject digest, approver eligibility, expiration and required quorum.
  • Decision endpoint rechecks live authorization, subject freshness and separation-of-duties policy.
  • Database transaction commits decision, audit and outbox event atomically.
  • Layer 3 receives an idempotent approval event and checks its workflow wait condition.
  • Release deployment adapter must independently recheck approval validity at execution time.
Never allow the same agent that produced the artifact to approve its own quality verdict or deployment. Agents and service principals can never approve any subject kind.

Separation-of-duties policy: the default policy requires the approver to differ from the requester. The pilot-single-approver policy, allowed only for a single-tenant pilot organization, lets one human approve every subject kind; each such decision is recorded in audit with sodWaived=true.

15 · Event Router, inbox/outbox and projections

Layer 2 writes transactional outbox records for commands and consumes Layer 3 events into an inbox. This avoids lost commands and duplicate projection updates, but it does not promise exactly-once delivery.

Layer 2 TX: business change + audit + outbox
    -> dispatcher retries -> Layer 3 event admission
Layer 3: workflow transition + execution events
    -> authenticated callback / broker -> Layer 2 inbox
    -> dedupe(eventId) -> update projection + notify SSE
ControlImplementation
Inbox deduplicationUnique (producer, event_id); ignore exact duplicates
OrderingPer-execution sequence; buffer/reconcile gaps
Schema compatibilityExplicit schemaVersion; tolerant readers; contract tests
ReplayRebuild projections from retained event stream or snapshot + delta
Outbox retriesExponential backoff, dead-letter, alert, operator replay
Status freshnessShow lastEventAt, projectedAt, stale flag
SSEEvent IDs, Last-Event-ID resume, authorization recheck

Layer 3 event types consumed (v3.3): ExecutionAdmitted, ExecutionRejected, StageOutputProduced, WaitingForApproval, TaskStateChanged, TaskAwaitingReview, TaskMerged, StageEvaluated, IntegrationJobCompleted, IntegrationFailed, CandidateFrozen, GateEvaluated, DefectsRaised, VerificationCompleted, WatchdogStateChanged, UsageRecorded, ExecutionCompleted. StageOutputProduced creates the matching DRAFT record (§06); TaskAwaitingReview and WaitingForApproval create approval requests and notifications; WatchdogStateChanged to STALLED or ESCALATED is shown in Monitoring and notifies the project.

17 · Artifact and evidence access

19 · Budgets, quotas and cost accounting

Layer 2 checks admission limits and reserves budget; Layer 3 enforces real-time token/time/tool caps in the Harness. Both are necessary because preflight estimates are imperfect.

budget: available -> reserved -> partially_consumed -> settled
                            \-> released_on_failure
usage event: {executionId, taskId, meter, quantity,
              estimatedCost, currency, providerReceipt, eventId}

Reserve against tenant/project limits transactionally, reconcile Layer 3 usage events idempotently, and surface estimated vs settled cost. On crash or lost events, an operator reconciliation job compares reservations, workflow outcomes and provider receipts.

27 · Identity, authentication and session architecture

Decision: use OIDC Authorization Code + PKCE through a Backend-for-Frontend (BFF). An external IdP handles passwords, recovery, MFA, token issuance and federation. MayanForge stores an internal user profile mapped to immutable issuer+subject, never to mutable email alone.

Browser → BFF → OIDC Provider → BFF callback → session store → Layer 2 APIs

Browser holds Secure, HttpOnly, SameSite session cookie; refresh tokens remain server-side and encrypted. CSRF tokens protect state-changing requests. Redirect URI and state/nonce are verified; step-up required for privileged operations.

Lifecycle and threat handling

  1. Invitation creates a pending membership, not a password account.
  2. OIDC callback validates issuer, audience, nonce, state, expiry and signature; account linking requires explicit trusted policy.
  3. Provision user via issuer+subject and transactionally accept invitation; reject wrong organization or expired invitation.
  4. Session has idle and absolute expiration, rotation, revocation, device metadata and audit receipt.
  5. Deactivation revokes application sessions and access grants; IdP disablement remains separately administered.

Tradeoff: OIDC provider is replaceable. Never claim that an application logout invalidates all IdP sessions unless the provider supports that mechanism.

28 · Organization, membership, RBAC/ABAC and user lifecycle

Aggregate boundaries: UserProfile (global identity), Organization (tenant), Membership (user ↔ organization), Team, RoleDefinition, RoleBinding, Invitation and PolicyVersion. A user may belong to multiple organizations with different roles.

Recommended baseline roles

RoleScopeTypical permissions
Platform operatorPlatformInfrastructure administration; not automatic tenant data access
Organization ownerOrganizationManage members, policies, quotas, billing settings
Organization adminOrganizationInvite users, assign allowed roles, manage projects
Project maintainerProjectModify project artifacts and request executions
EngineerProjectEdit permitted drafts, inspect runs and evidence
ReviewerProjectApprove assigned immutable subjects, subject to separation of duties
ViewerProjectRead authorized non-sensitive resources

Authorization: allow only if authenticated identity, active membership, scoped role binding, project ACL, operation, resource state and policy all permit. A reviewer cannot approve their own change where separation of duties is required; the audited pilot-single-approver policy (§14) is the only exception. Recheck at command admission and at Layer 3 effect boundary. Tenant IDs are derived from verified membership, never trusted solely from a client-supplied body.

Lifecycle: invited → active → suspended/deactivated; membership removal revokes scoped access and pending invitations; historical approvals/audit retain immutable actor references per retention policy. Support service principals separately from human users, with short-lived credentials and narrowly scoped permissions.

30 · Data model extensions and transactional consistency

The following is illustrative PostgreSQL DDL; migration scripts must be reviewed and tested before use. Foreign keys and unique constraints enforce tenant-scoped integrity. Sensitive token values are never stored in plaintext.

CREATE TABLE app_users (
 id uuid PRIMARY KEY, issuer text NOT NULL, subject text NOT NULL,
 display_name text, email_normalized text, status text NOT NULL,
 created_at timestamptz NOT NULL DEFAULT now(),
 UNIQUE (issuer, subject));
CREATE TABLE organizations (id uuid PRIMARY KEY, name text NOT NULL, status text NOT NULL);
CREATE TABLE memberships (
 org_id uuid NOT NULL REFERENCES organizations(id),
 user_id uuid NOT NULL REFERENCES app_users(id),
 status text NOT NULL, version bigint NOT NULL DEFAULT 0,
 PRIMARY KEY(org_id,user_id));
CREATE TABLE role_definitions (
 org_id uuid NOT NULL REFERENCES organizations(id),
 role_id text NOT NULL, permissions jsonb NOT NULL,
 version bigint NOT NULL, PRIMARY KEY(org_id,role_id));
CREATE TABLE role_bindings (
 org_id uuid NOT NULL, user_id uuid NOT NULL, role_id text NOT NULL,
 PRIMARY KEY(org_id,user_id,role_id),
 FOREIGN KEY(org_id,user_id) REFERENCES memberships(org_id,user_id),
 FOREIGN KEY(org_id,role_id) REFERENCES role_definitions(org_id,role_id));
CREATE TABLE invitations (
 id uuid PRIMARY KEY, org_id uuid NOT NULL REFERENCES organizations(id),
 email_normalized text NOT NULL, token_hash text NOT NULL UNIQUE,
 status text NOT NULL, expires_at timestamptz NOT NULL,
 accepted_by uuid REFERENCES app_users(id));
CREATE TABLE app_sessions (
 id uuid PRIMARY KEY, user_id uuid NOT NULL REFERENCES app_users(id),
 session_hash text NOT NULL UNIQUE, expires_at timestamptz NOT NULL,
 revoked_at timestamptz, last_seen_at timestamptz);

Consistency

Invitation acceptance, membership activation and audit event are committed atomically. Execution request, quota reservation and outbox event are committed atomically. Outbox delivery is at-least-once; consumers deduplicate using command IDs. Authorization cache entries are invalidated on membership/role changes and expire quickly; critical approvals always recheck authoritative state.

Important: session store and refresh-token vault may be separate from PostgreSQL. DDL is logical, not a production-ready security implementation.
